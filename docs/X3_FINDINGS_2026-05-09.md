## The smoking-gun observation

The driver's current state, as of 2026-05-09 20:51:

```
driver_trip_state.driver_id        = UjT1hE9eBXh2q95aSZYOkzDJ8lo1
driver_trip_state.current_offer_id = 7770
driver_trip_state.heartbeat_at     = 2026-05-09 20:51:07.364948+00
```

The pointer is `7770`. But:

```
decision_log.id = 7770    → driver_id matches, created_at = 2026-04-26 15:57:52  (April 26)
offer_history.id = 7770   → decision_log_id = 8394, created_at = 2026-05-07 15:40:35,
                            app_verdict = DECLINE, actual_pickup_at = NULL  (May 7)
```

These are two unrelated rows. They share the integer `7770` because `decision_log.id` and `offer_history.id` are independent BIGINT sequences. Neither the April 26 ride nor the May 7 DECLINEd offer has anything to do with the other.

`current_offer_id = '7770'` was set at some point referring to one of these rows. The system has been operating under that pointer for **13 days** and never advanced it past 7770, despite 11 subsequent ACCEPTed rides.

## The contradictory comments

In `driver_heartbeat.py:_execute_action`, the FirePickup branch contains two adjacent code blocks with mutually contradictory comments:

**Block 1** — UPDATE `pickup_market_signals` (lines 179-194):
```
# pms.offer_id REFERENCES decision_log(id), but action.offer_id is
# offer_history.id; translate via subquery at schema boundary.
UPDATE app_private.pickup_market_signals
SET ...
WHERE offer_id = (
    SELECT decision_log_id FROM app_private.offer_history
    WHERE id = %s::bigint
)
```

This subquery says: "treat `action.offer_id` as `offer_history.id`, look up its `decision_log_id`, use that to find the matching `pickup_market_signals.offer_id`."

**Block 2** — UPDATE `offer_history` (lines 196-215):
```
# [α-fix] offer_history: canonical PUDO record. action.offer_id
# IS offer_history.id, so target it directly. Rowcount guard fires
# on zero-row UPDATE — that means the offer doesn't exist (logged
# WARNING + return failure).
UPDATE app_private.offer_history
SET actual_pickup_at = NOW(), ...
WHERE id = %s::bigint
```

Both comments declare `action.offer_id` to be `offer_history.id`. So the UPDATE targets `WHERE offer_history.id = action.offer_id`.

But `wai_offer_id` populated in PDC for these dispatches shows values like `7770`, `7769`, `7763` — and those values cannot be reliably interpreted as either `decision_log.id` or `offer_history.id`. They might be either. Sometimes both rows exist for the same integer (different rows), sometimes only one. The system has no provenance metadata on which "kind" of ID it's holding.

## The α-fix warnings that should have fired but didn't

`_execute_action` has explicit rowcount guards at line 216-222 (FirePickup) and the FireDropoff equivalent. If the UPDATE matches zero rows in `offer_history`, a `WARNING [α-fix]` log is supposed to fire and the function returns `False, "fire_pickup_zero_rows"`.

**Cloud Run logs grep over `--limit=500` for `α-fix` OR `0 rows` returned zero matches.**

Three possible explanations:

- **(a)** The α-fix code shipped *after* the most recent dispatched row (May 7). Sample size since deploy is too small to have triggered the warning.
- **(b)** The UPDATE matches `cur.rowcount == 1` because `offer_history.id = action.offer_id` finds *some* row (just the wrong row — the May 7 DECLINEd 7770 instead of the April 26 ACCEPTed 7770's offer_history child). So the rowcount guard never fires, but the write lands on the wrong row.
- **(c)** Cloud Run logs filter or buffer behavior is hiding the warnings.

We did not eliminate any of these in this session.

If (b) is the live behavior, the wrong row is getting `actual_pickup_at = NOW()` written to it — but the May 7 row 7770 still has `actual_pickup_at = NULL` per the recon. So either the transaction rolled back after the UPDATE (some downstream INSERT raised), or (b) is wrong and the right answer is (a).

---

## The transactional question

`_execute_action` returns `True, None` on success. The wrapping heartbeat handler then writes the PDC row with `dispatch_executed = true`. **PDC writes and offer_history UPDATEs share the same `conn` and presumably the same transaction.** If anything raises between `_execute_action` returning success and the final commit, `conn.rollback()` would erase both — but PDC rows clearly persist (we have 69,090 of them). So either:

- The PDC INSERT happens AFTER the commit (different transaction)
- Some specific exception is being caught and the rollback is partial / scoped
- The α-fix warning IS firing but not reaching the logs we read

This question matters for the fix design. We cannot patch the offer_id semantic issue without first knowing what the transaction boundaries actually are.

## What is now known

1. **The `offer_id` semantic is unstable.** The system carries an integer through `current_offer_id`, `WAIMatch.offer_id`, `dispatch.FirePickup.offer_id`, and `_execute_action`'s SQL bindings without a single point that declares "this integer is `decision_log.id`" or "this integer is `offer_history.id`." Comments in `_execute_action` simultaneously claim both.
2. **The `current_offer_id` pointer has been stuck on `7770` for 13 days** through 11 ACCEPTed rides on the same driver, none of which produced PUDO writes.
3. **`dispatch_executed = true` is misleading.** It means `_execute_action` returned `(True, None)`, not that the side-effect actually committed to its target table. The 165 rows with this flag should not be assumed to represent successful PUDO commits.
4. **`actual_pickup_at` / `actual_dropoff_at` writes are zero across the entire production dataset of recent rides.** Auto-detection is functionally non-existent for the launch.
5. **The Horizon Budget GC fix that shipped in this session does not address this.** Horizon GC operates on `prev_row` selection in `decisions/logger.py` at offer-arrival time. It does not run during heartbeats and would not affect the auto-detection write path.

---

## What is not known

1. **Which kind of ID does `current_offer_id` actually hold?** Architecturally — what was its declared meaning when the column was created? We have not located the original schema-design doc or commit.
2. **Where does `current_offer_id` get written?** `dispatch_executed = true` implies `_execute_action` ran. The function calls `queue.bind(action.offer_id, cur)` in the FirePickup branch. The DriverQueue layer is presumably what writes `driver_trip_state.current_offer_id`. We did not read that layer in this session.
3. **What does `WAIMatch.offer_id` semantically represent?** `where_am_i.py:1746` constructs `WAIMatch(...)` — we did not read which field of the upstream offer it pulls into the `offer_id` attribute.
4. **Whether the integer-collision hazard is provable as the cause.** We see that `decision_log.id = 7770` (April 26) and `offer_history.id = 7770` (May 7) coexist. We have not proven that this collision is what's causing the writes to fail; only that it's a sufficient condition for confusion.
5. **The α-fix deploy timeline.** When did the rowcount guard ship? If the 165 dispatched rows predate the α-fix, then the warnings literally couldn't have fired for them. If they postdate it, we have a different bug.

## The questions for the next session

These are not solutions. They are the questions a fix design has to answer before code can land:

1. **What is the canonical ID of an "offer" in PuddleJumper?** Pick one — `decision_log.id`, `offer_history.id`, or a new UUID minted at offer-creation time. Every layer (queue, WAIMatch, dispatch, offer_history-writer) has to agree.

2. **What is the migration path?** Existing rows have stuck `current_offer_id` pointers. A schema change has to be safe across the existing data. There is at least one driver in production right now (you) whose pointer is stale.

3. **Where do the "translation subqueries" go?** Today, `_execute_action` does both styles in a single function. Either we eliminate the translation (one ID kind for all consumers) or we centralize it (a single resolver that exposes both forms with provenance).

4. **What's the test surface?** 569 tests pass today, but they pass against the same flawed model. Some of them are validating broken behavior. Identifying which tests are "true" assertions vs "shape-of-the-bug" assertions is part of this sprint.

5. **Is there a quick partial-fix that gets PUDO writes working for the launch, while a fuller identity-layer cleanup happens post-launch?** Or does this *have* to be done correctly before launch because partial fixes will keep accumulating debt? Honest answer required — the temptation to ship a band-aid will be strong.
